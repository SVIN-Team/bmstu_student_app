# Соответствие приложения методологии 12 Факторов (12-Factor App)

В данном документе описано, как архитектура и реализация проекта `bmstu_student_app` соотносятся с принципами разработки современных веб-приложений "Двенадцати факторов" (12-Factor App).

## 1. Кодовая база (Codebase)
**Одна кодовая база, отслеживаемая в системе контроля версий, – множество развёртываний.**
Проект представляет собой единый монорепозиторий (`bmstu_student_app`), в котором версионируются бэкенд, фронтенд, скрипты развертывания и инфраструктурные сценарии (Docker, Makefile). Для любого окружения используется одна и та же кодовая база.

## 2. Зависимости (Dependencies)
**Явно объявляйте и изолируйте зависимости.**
Все зависимости проекта строго зафиксированы и изолированы:
- **Бэкенд:** Зависимости Go описаны в `go.mod` и зафиксированы в `go.sum`. Приложение собирается внутри Docker.
- **Фронтенд:** Использует `package.json` и `package-lock.json` для строгой фиксации версий npm-пакетов.
- Полная изоляция среды выполнения обеспечивается с помощью Docker-контейнеров для каждого компонента.

## 3. Конфигурация (Config)
**Сохраняйте конфигурацию в среде выполнения.**
Код приложения полностью отделен от конфигурации. Параметры передаются через переменные окружения (`.env` файлы). Бэкенд считывает эти данные на старте из конфигов и переменых окружения, благодаря чему один и тот же Docker-образ можно разворачивать с разными настройками.

## 4. Сторонние службы (Backing Services)
**Считайте сторонние службы подключаемыми ресурсами.**
СУБД (PostgreSQL) и брокер/кеш (Redis) не встроены в слои приложения. Они поднимаются отдельными контейнерами и подключаются по URL (connection strings: `postgres://...` и `redis://...`). Замена локального Redis или Postgres на облачные управляемые решения (например, Yandex Cloud Managed Databases) потребует изменения лишь переменных окружения без изменения кода приложения.

## 5. Сборка, релиз, выполнение (Build, release, run)
**Строго разделяйте стадии сборки и выполнения.**
В проекте реализовано четкое разделение:
- **Сборка (Build):** Выполняется с помощью `Makefile` (`make build-all`) и сборок Docker-образов (`Dockerfile` для Go-приложения и Node.js/Vite среды). Исходный код превращается в исполняемый бинарник и статику.
- **Релиз (Release):** Образ приложения + конфигурация среды (`.env`, `config.yaml`).
- **Выполнение (Run):** Запуск через `docker compose up -d` или индивидуальные команды для контейнеров (`make run-front`, `make run-back`).

## 6. Процессы (Processes)
**Запускайте приложение как один или несколько процессов, не сохраняющих внутреннее состояние (stateless).**
Go-бэкенд является приложением без сохранения состояния (stateless). Любые разделяемые данные (очереди, слоты, пользователи) хранятся в PostgreSQL, а быстро меняющееся состояние или сессии токенов могут использовать Redis. Контейнер с приложением может быть убит и перезапущен без потери пользовательских данных.

## 7. Привязка портов (Port binding)
**Экспортируйте сервисы через привязку портов.**
Сервисы внутри проекта полностью самодостаточны:
- Бэкенд на Go слушает порт `8080` и обрабатывает HTTP-запросы напрямую из бинарника, без необходимости интеграции в тяжеловесный внешний веб-сервер.
- Фронтенд работает на порту `5173`.
Проброс портов во внешнюю среду управляется на уровне `docker-compose.yml` (например, `ports: "8080:8080"`).

## 8. Параллелизм (Concurrency)
**Масштабируйте приложение с помощью процессов.**
Горизонтальное масштабирование приложения легко реализуется благодаря stateless архитектуре бэкенда. При необходимости обработки бóльшего объема трафика можно запустить дополнительные инстансы (контейнеры) Go-бэкенда за балансировщиком нагрузки. Внутри процесса Go эффективно реализует параллелизм за счет использования горутин (goroutines).

## 9. Утилизируемость (Disposability)
**Максимизируйте надежность с помощью быстрого запуска и корректного завершения работы.**
Go компилируется в один бинарный файл, который запускается практически мгновенно. Контейнеры могут быть безопасно остановлены командой `docker compose down`. Данные персистентны благодаря механизму Docker Volumes. Приложение готово корректно прервать работу при получении сигнала SIGTERM.

## 10. Паритет Dev/Prod (Dev/prod parity)
**Держите окружения разработки и production максимально похожими.**
Использование Docker и Docker Compose гарантирует, что стек (Go, Postgres 16, Redis 7, Node) идентичен на ноутбуке разработчика и на сервере развертывания. Сокращен разрыв:
- *Во времени:* легкий релиз новых сборок (`make build-all`).
- *В инструментах:* база данных один-в-один совпадает локально и на сервере.

## 11. Журналирование (Logs)
**Рассматривайте журнал, как поток событий.**
Приложение пишет логи в стандартные потоки вывода (`stdout`/`stderr`), используя внутренний логгер (`util/logger`). Бэкенд не управляет файлами логов, ротацией или их хранением. Эту задачу берет на себя среда выполнения (Docker engine), которая перехватывает потоки вывода (доступно через `docker logs`), маршрутизуя их при необходимости во внешние системы.

## 12. Задачи администрирования (Admin processes)
**Выполняйте задачи администрирования/управления с помощью разовых процессов.**
Сценарии миграции инициализируются при старте базы (через встроенный механизм `docker-entrypoint-initdb.d`), а скрипты управления, вроде наполнения БД тестовыми данными, запускаются изолированно как разовые процессы.
